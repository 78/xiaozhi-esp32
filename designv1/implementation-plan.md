| --- | --- |
| `D:\work\xiaozhi-realtime` | 保留现有工作现场；预期为 develop，实际分支和未提交内容以实施前检查为准 |

两个 worktree 共享 Git 提交历史，工作文件、索引和构建目录分别独立。目录或分支已存在时先检查其用途，不覆盖、不强制重置。

- [Go Realtime Debug 设计](go-realtime-debug-design.md)：透明代理、请求标识关联、三条基础音轨、设备状态通道及调试网页。

## 3. 阶段一：盘点并保留现有工作现场

1. 检查当前分支、提交位置、已有 worktree 及工作区状态，包括未提交修改和未跟踪文件。
2. 检查本地及远程跟踪的 `main`、`develop`，必要时获取远程分支信息，明确新分支所用 main 的具体提交。
3. 记录当前 develop 的参考提交，以及未提交文件的范围。未提交内容不会自动出现在新 worktree 中，后续查阅时需同时参考原目录。
4. 确认 `designv1` 文档完整，避免创建分支时遗漏尚未提交的设计文件。

完成条件：明确基线提交与现有修改范围；原目录内容完整保留，无分支切换、强制重置或清理操作。

## 4. 阶段二：创建新 worktree 并迁入设计

1. 确认目标路径与分支名可用，从选定 main 提交创建 `feature/realtime-v1` 及 `D:\work\xiaozhi-realtime-v1` worktree。
2. 将当前 `designv1` 复制到新 worktree，原目录副本继续保留，不移动或删除。
3. 核对文件内容、Git 状态和文档相对链接。文档引用的 develop 专有材料若 main 中不存在，应补充必要摘要、明确旧目录参考位置，或有选择地复制相关参考文档，避免留下无法访问的依据。
4. 将设计文档作为独立改动整理；后续设计更新以新 worktree 中的版本为准。

完成条件：新分支起点可追溯到选定 main；新目录具备完整、可阅读的设计依据；原工作现场不受影响。

## 5. 阶段三：建立 main 功能基线

1. 核对新 worktree 中的仓库规则、板型名称、构建入口及依赖。
2. 使用 ESP-IDF `release/v6.1`，核实实际版本；最低 SDK 要求遵循仓库政策。
3. 按规范构建目标板，运行适用的主机测试，记录环境错误与跳过项。
4. 在具备设备条件时验证原有配网、小智协议、录音和播放，记录固件提交、配置与测试结果。

如果 main 缺少目标硬件所需支持，先识别并引入最小必要适配，单独说明其来源，避免将适配后的结果误记为未经修改的 main 基线。

完成条件：得到可复现的构建和功能基线；未验证项目与阻塞原因明确，后续回归有对照依据。

## 6. 阶段四：筛选 develop 的可复用代码

按文件、符号与提交历史查阅，并与 main 比较，重点评估：

- 阿里云连接、配置、事件解析及音频收发。
- NSNet2 降噪和目标板音频链路。
- 上行连续性、编码调度与有界发送队列修复。
- 长回复缓冲、播放取消及迟到音频处理。
- 设备状态、样本计数、队列统计与原始 PCM 采集点。
- Go 透明代理、音频提取、记录器及已有调试页面。

独立且依赖清晰的提交可评估 cherry-pick；混有多项实验或临时调试的提交，参考后只迁入必要实现。每项同时核对依赖、目标代码差异和新设计要求，不整体合并 develop。

迁移记录至少包含原提交或文件位置、复用目的、依赖项、实际调整及验证结果。历史测试记录作为参考，迁入后的代码仍需重新验证。

完成条件：形成可逐项迁入的功能清单，每个项目的来源和必要性明确。

## 7. 阶段五：分阶段实现与验收

### 7.1 阿里云 Manual

先打通配置读取、鉴权连接、单轮收音、结束输入、回复接收和完整播放。处理错误、取消与重连，确认新一轮不会继承旧音频。

### 7.2 阿里云 Auto 半双工

接入自动轮次检测。回复阶段关闭上行，服务器音频结束且本地解码、播放队列及在途输出排空后，清理旧采集与发送数据再恢复监听。不得补传播放期间积累的麦克风录音。

### 7.3 按键与设备显示

双击 BOOT 切换 Manual / Auto，协调现有单击和其他按键行为。Speak / Listen 同时显示当前模式；活动轮次中切换需正确取消和清理旧任务。

### 7.4 Go Debug 尽早介入联调

在固件开发期间先接通透明代理、原始消息、reqid 等标识及上下行音频记录，辅助验证 Manual / Auto。随后接通 ES8311 原始采集和设备轻量状态通道，完善轮次关联、时间线、试听、检索与诊断包。

此项可随固件阶段交替推进，避免到开发末期才具备排障能力。完整音频诊断必须覆盖 ES8311 原始采集、云端上行与云端下行三条基础音轨。

### 7.5 统一配置网页

在网络与服务配置行为明确后整合页面：保留共用配网入口，分别提交网络与服务配置，保存小智和阿里云两套参数，移除模式切换。完善连接反馈、密钥处理和手机端简洁布局。

## 8. 验证与提交原则

每项迁移或功能改动保持聚焦，执行仓库要求的检查，避免一次引入大批无法归因的变化。提交与实现阶段尽量对应，使问题可以定位和回退。

- 主机测试：记录通过、失败、跳过和环境限制，不将跳过记为通过。
- 固件构建：采用规范板型构建入口，注意构建脚本会改变本地配置与构建状态。
- 音频实机：覆盖采集、降噪、人声完整性、上行连续性、长回复、取消、模式切换及重连。
- Auto 实机：确认播放期间无云端上行，本地播放完成后恢复，且尾音和旧缓存不引发错误轮次。
- Go Debug：确认转发顺序与内容不变，诊断过载缺口可见，音频格式和标识关联真实可追溯。
- 网页与配网：覆盖首次配网、更换网络及失败恢复、配置保存和服务连接反馈、两套参数保留及手机布局。

配置、凭证与大流量录音按仓库及调试设计要求处理，不将本机敏感信息和测试数据混入代码提交。构建通过与实机验收分别报告；其他板型、芯片或传输路径的覆盖范围遵循仓库规则并明确记录。

## 9. 完成标准

1. 新 worktree 和开发分支建立于明确的 main 提交，设计文档完整迁入。
2. 原 develop 工作目录、未提交修改及参考证据保留。
3. 复用 develop 的实现有明确来源，迁入范围聚焦并完成相应验证。
4. Manual、Auto 半双工、BOOT 模式切换、屏幕显示、统一网页和 Go Debug 按设计实现并完成适用验收。
5. 最终报告包含代码改动、构建和测试结果，以及仍需实体硬件或其他目标验证的项目。
