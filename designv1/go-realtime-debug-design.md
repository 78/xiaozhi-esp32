# Go Realtime Debug 程序设计约定

日期：2026-11-16
状态：讨论结论，作为后续实现依据；尚未完成代码实现与实机验收。

## 1. 定位与范围

延续原 [Go 调试代理设计摘要](historical-reference.md#调试代理) 的 WebSocket 透明代理方案，围绕 [Manual / Auto 交互约定](aliyun-manual-auto-design.md) 组织调试信息。本文补充当前讨论的方向，未涉及的原设计细节在实现时继续核对。

设备通过 URL 选择直连阿里云或经过 Go Proxy。Go 原样转发双向应用层消息，同时旁路记录信令、音频与关联标识，帮助判断问题发生在硬件采集、设备处理、网络发送、云端回复还是本地播放阶段。

正式设备配置放在统一设备配置网页。Go 网页专注调试，不提供 Manual / Auto 切换；模式由设备上报，用户通过双击 BOOT 切换。旧 TCP Collector 可先保留兼容入口，是否与新诊断通道复用在实现时确认。

## 2. 数据通道与转发边界

- WebSocket 代理通道：设备与阿里云之间双向转发，提取上行和下行音频。每个方向维持单一 FIFO，不因记录或解析而重排、改写、合并或丢弃正式消息。
- 设备诊断通道：接收 ES8311 原始 PCM、设备状态事件和轻量统计。原始采集无法从云端协议消息还原，需要设备独立上传。
- 记录通道：使用独立、有界的异步队列落盘。记录失败只影响诊断副本，缺口必须可见。

代理接收、转发尝试与转发成功分别记录。发送调用成功不代表阿里云已经接受或处理，远端处理需由对应云端事件证明。

## 3. 请求与会话标识

分别保留以下标识，不将其混为同一种请求编号：

| 标识 | 来源与用途 |
| --- | --- |
| 云端 request_id / reqid | 从握手响应或服务端事件提取实际返回值，用于云端排障；记录原字段名、来源及作用范围 |
| session_id、response_id、event_id 等 | 从协议提取，用于关联会话、回复、事件和取消行为 |
| 本地连接与轮次追踪 ID | Go 自行生成，支持没有云端 reqid 时的本地检索 |
| 设备 boot_id、连接代次与设备单调时间 | 区分重启、重连并关联设备侧诊断数据 |

WebSocket 长连接可能包含多轮对话，reqid 不一定代表某一轮。只有协议明确提供关联时才绑定；未知字段显示“未返回”或“未关联”，不得按相邻时间推断为确定关系。本地轮次组织如需启发式推断，应明确标注推断来源。

网页支持查看、复制及按 ID 检索，诊断包保留关联关系。设备诊断通道与代理连接的对应关系需显式建立，不能只凭 IP 或时间邻近绑定。具体阿里云字段和握手响应可获取能力在实现阶段核实。

## 4. 音频记录

### 4.1 三条基础音轨

| 音轨 | 采集来源 | 用途 |
| --- | --- | --- |
| ES8311 原始采集 | 设备 I2S 读取完成后、重采样和 NSNet2 等软件处理之前旁路上传 | 确认硬件实际采到了什么，分析底噪、串扰和近端语音完整性 |
| 云端上行 | 从设备发往阿里云的代理消息提取 | 检查处理和发送后的语音，与原始轨对照 |
| 云端下行 | 从阿里云回复的代理消息提取，按 response_id 等组织 | 检查云端实际返回的内容 |

ES8311 原始音轨属于完整音频诊断的基础记录，不从代理音频推算或还原。这里的“原始”指未经后续软件处理的数字采集，仍包含 ES8311 硬件输入增益等配置的影响。

原始 PCM 不做增益归一化、降噪或静音裁剪。保存实际读取的声道布局；若包含麦克风和硬件参考声道，两路都保留并明确标注，不混合成单声道。实际声道含义须核对板型与驱动实现。

记录准确采样率、声道数、有效位宽、存储布局、字节序、样本格式、每帧样本数及音频处理阶段，不能根据文件名猜测格式。不同格式分段保存。压缩音频保留原始编码，确认格式后再生成可试听文件。

### 4.2 设备侧原始采集约束

原始采集 tap 只做有界复制和入队，通过独立任务异步发送，不阻塞正常采集、音频处理或云端对话。队列与内存预算保持有界，具体容量经目标设备测量后确定。

启用完整音频诊断时，Auto 播放期间继续记录 ES8311 原始音频，同时维持云端上行关闭，以观察扬声器回采与余响。诊断开关入口在实现时确定，采集记录应注明启用范围。

诊断连接断开或队列溢出时丢弃诊断副本并记录缺口，不无限积压，也不假装补齐。重连后使用序号和样本位置显示不连续。

### 4.3 时间、样本与记录真实性

每个片段记录音轨、序号、设备单调时间（若可得）、Go 接收时间、文件偏移、字节数、样本位置、格式段及明确关联的请求和回复标识。

设备时间与 Go 接收时间分别保存。未经时钟校准不能将两者直接解释为精确单向延迟；不同采样率和处理延迟下，也不能仅凭相同样本序号强行对齐。原始轨与上行轨依据可用时间和样本信息对照，并标出对齐的不确定性。

Auto 播放期间没有上行属于“暂停上传”，与诊断缺口或业务丢帧分别展示。不将暂停前后的语音无提示地拼接为连续录音；时间线保留暂停和缺口，导出时附带分段信息。

云端下行不等于设备实际播放录音。取消后代理仍可能收到音频，应标记取消事件和设备播放进度。设备上报播放完成也不等于独立声学测量；确认物理扬声器输出仍需实机录音。

### 4.4 可选专项音轨

按需增加 NSNet2 输出及实际提交播放接口的 PCM，帮助进一步定位处理或播放问题。专项采集不替代三条基础音轨，并需评估额外带宽与实时性影响。

## 5. 设备状态与统计

仅靠代理消息无法知道设备本地是否已经播完，因此需要设备通过诊断通道上报：

- 当前 Manual / Auto 模式、运行状态及状态切换。
- 开始收音、上行关闭和恢复，以及本地播放开始、完成、取消。
- 编码和发送丢帧、播放队列积压、采样计数及诊断记录缺口等轻量统计。

用这些事件关联云端 VAD、首个回复音频、服务器音频结束及本地队列排空，验证 Auto 是否在本地播放完成后恢复上行。设备实际可提供的计数及含义在实现时核对，避免将“提交播放”当成“已经发声”。

## 6. 存储与音频导出

每个会话一个目录，连续追加写入数据，用索引组织片段与轮次，不为每个音频包创建小文件。建议结构：

```text
会话目录/
  manifest.json          会话标识、设备版本、格式段和完整性统计
  events.jsonl           信令、音频片段、状态及关联索引
  payloads.dat           原始双向 WebSocket 应用消息
  es8311-raw-*.pcm       原始采集，按格式段保存
  uplink-*.pcm           确认为 PCM 的上行音频
  downlink-*.pcm         确认为 PCM 的下行音频
```

非 PCM 音轨保存实际编码，文件名与元数据反映真实格式。网页按索引生成单轮或分段试听与 WAV 下载，原始多声道数据始终保留；试听时可选择麦克风或参考声道。

记录器异步落盘，磁盘慢或队列满时优先维持正式转发，明确记录 trace_gap。设置单会话大小、总磁盘量及保留时间上限；达到录制上限时标明截断，不将部分记录显示为完整。

诊断包包含会话清单、事件、原始消息、音频及关联标识和完整性信息。鉴权 Header 与 API Key 不写入日志或诊断包；沿用原设计的内网运行、访问和数据保留边界。

## 7. 调试网页

采用左侧会话列表、右侧对话详情的布局，默认展示易读的对话与音频，原始消息和详细统计折叠。

- 会话概览：设备和阿里云连接状态、模式、时长、错误及记录完整性。
- 按轮对话：用户转写、模型回复、原始采集片段、上行及下行音频；无法确定轮次关联时保留未关联项。
- 时间线：并列查看原始采集、云端上行与下行，以及上行暂停、VAD、播放完成和取消等事件。支持对照试听和定位，不掩盖暂停或缺口。
- 详情：reqid、session_id、response_id、event_id 等可复制和搜索，原始消息按需展开。
- 导出：单轨、单轮或格式段音频下载，以及完整诊断包导出。

波形使用降采样摘要，音频按需读取，避免一次性将整场录音加载进浏览器。

## 8. 实施与验收重点

第一阶段完成透明代理、基本会话记录、上下行音频提取与试听；完整音频诊断交付还需接通 ES8311 原始采集及设备状态通道。随后完善轮次和 ID 关联、时间线与诊断包。

验收覆盖：

- 直连与代理行为对比，双向消息顺序和边界不被记录功能改变。
- reqid 等标识按实际协议记录，缺失和关联不明确时正确标注。
- 原始 PCM 声道与格式正确，可对照上行确认语音完整性。
- Auto 播放期间原始轨连续采集、云端上行暂停，播放完成后恢复且不补传旧录音。
- 长回复、取消和迟到音频、无音频回复、断线与重连的记录正确。
- 诊断通道断流、磁盘慢或满、记录队列溢出时缺口可见，正常对话不被诊断任务阻塞。
- 音频试听、分段下载、按 ID 搜索和诊断包可以准确追溯原始数据。

本文件仅整理设计。采集点、协议字段、时钟关联、资源预算与音频真实性均需后续代码核对和实体设备验证。
